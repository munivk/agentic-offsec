# Evaluation (full detail)

The full evaluation behind the one-page `ANALYSIS.md`: a governed, read-only, impact-gated
triage agent on top of Nuclei, run against OWASP Juice Shop (authorized sandbox) and compared
against a scripted baseline. Every number here comes from `evidence_clean/`, and the table is
generated by `python evidence_table.py` (output: `evidence_clean/TABLE.md`).

## Setup

- **Agent:** Claude Sonnet 4.6 on AWS Bedrock (`us.anthropic.claude-sonnet-4-6`) drives a
  hand-written loop with two tools (scoped detection scan, read-only GET). Every action is
  scored by an impact gate before it runs. Every step goes to a hash-chained audit log, and
  every tool call has a number (`call N`) that the report must cite.
- **Baseline (control):** `baseline.py`, plain Nuclei over the same passive tags in one pass,
  then rule-based triage (dedupe by template ID, drop header noise, sort by severity). No model.
- **Target:** OWASP Juice Shop in local Docker, restarted before every run. The notable
  exposures a Nuclei-class tool can see are a public Prometheus `/metrics` endpoint and
  public Swagger docs.
- **Versions:** Nuclei v3.11.1, nuclei-templates v10.5.2 (11,835 web templates; counts by tag
  in `evidence_clean/template_counts.txt`).
- **Runs:** 3 baseline runs and 3 agent runs (`run_clean.sh`, 2026-11-24 00:54 to 01:43 UTC),
  a deterministic gate demo, and one live, human-in-the-loop gate run (01:48 to 02:01 UTC).
- **Tied to the code:** every run's audit log records the code fingerprint
  `6a82b4b0a258e9da…` (`python fingerprint.py` reproduces it) and the policy hash
  `890fb475564ef849…`. All four model runs carry the same two values. All five audit chains
  verify (`evidence_clean/verify.out`, plus the live gate log).

## Assumptions

- **Authorization.** The only target is a local Juice Shop container I control; the host
  allowlist in code permits nothing else.
- **Ground truth.** The yardstick is what a Nuclei-class detection tool can see on this
  target: the public `/metrics` endpoint and the public Swagger docs. Juice Shop's
  business-logic and authentication flaws are out of reach for detection templates, so they
  are reported as untested rather than counted as misses.
- **Comparison.** The baseline runs the same passive tags, so any difference comes from the
  agent's decisions, not a wider scan.
- **Cost.** Estimated from Bedrock-reported tokens at Anthropic's list price; actual Bedrock
  regional pricing is about 10% higher. Engineer time is not included.
- **Sample.** Three runs per arm on one target: enough to see behavior, not to measure
  reliability.

## Results

| | Scripted baseline (3 runs) | Agent (3 runs) |
|---|---|---|
| Found `/metrics` and Swagger | 3 of 3 | 3 of 3, each confirmed with a read-only GET (calls 3 and 4 in every run) |
| Wall-clock | 7.4 min every run (442.3 to 443.4 s) | 9.9, 7.4 and 9.2 min |
| Cost per run | $0 | $0.069 to $0.074, estimated: Bedrock-reported tokens (12.3k to 13.7k input, 2.1k to 2.4k output) at Anthropic's list price for Sonnet 4.6, $3 / $15 per million (platform.claude.com/docs/en/about-claude/pricing). Bedrock regional endpoints, used here, cost about 10% more. |
| Scan timeouts | 0 | 1 per run, always the first `exposure, misconfig, panel` scan; each kept its partial findings (2, 1 and 10) |
| Output | Flat list: 14 raw, 7 deduped, 6 prioritized | Prioritized report (4 to 5 findings) with severity, reason, action, confidence, and the `call N` that observed each finding |
| Severity of `/metrics` | medium (template default) | MEDIUM in 3 of 3 runs |
| Severity of Swagger | info (template default) | MEDIUM in 3 of 3 runs |
| "What I did not test" section | No | Yes, every run |
| Gate decisions | n/a | Every scan low/auto; each run's `/metrics` fetch scored medium (sensitive path), ran, and was listed under "Flagged for human review" |

**Reading it honestly.** On coverage, the baseline is as good, faster and free. The agent does
not beat it there. What the agent adds is the judgment layer: it confirms findings with a GET,
explains why each matters, says what it did not test, and ties every finding to a logged call.
Severity was consistent across runs for both real findings. Three runs on one target is a
behavior check, not a reliability study.

So the recommendation is deterministic coverage with agentic judgment: the baseline owns
coverage, and the agent does prioritization and the human-facing report, inside the gate.

## The impact gate, live

`run_gate_live.py` is a single interactive run where the prompt allows the agent to *request*
active checks. Everything else is unchanged. Evidence:
`evidence_clean/audit_gate_live_20261124T014838Z.jsonl` (33 records, chain intact) and the
matching report.

- Call 4, `sqli`: scored HIGH, paused, **denied** by `human:operator` with a recorded reason.
  It did not run, and the agent did not retry it.
- Call 5, `default-login`: scored HIGH, paused, **approved** by `human:operator` with a
  recorded reason. The scan ran with `exclusions_lifted: ["default-login"]`. Every other
  excluded tag stayed excluded. It found nothing.
- The report says SQL injection was "DENIED by human operator at the impact gate. This was
  not run ... UNTESTED." That matches the log.
- The first scan (call 1) timed out and kept 12 partial findings; the report says so.

**Approval is not validation.** The approved `default-login` check ran cleanly and found
nothing, because Nuclei's default-login templates target known products' admin panels and
none exercises Juice Shop's `/rest/user/login`. The report hedges ("nuclei covers common
defaults but cannot guarantee exhaustive coverage"), yet its posture summary still says "No
default credentials were found", and Juice Shop ships seeded accounts with weak passwords. A
gate decides whether an action is safe to run, not whether it can answer the question.

In the 3 automated runs the agent never requested a high-risk action. In a development run
whose goal told it to test SQL injection, it refused at the prompt level, before the gate
(`evidence_development/`). That is good behavior, but it is prompt compliance, and that
depends on the model. The gate exists so that safety does not depend on the model choosing to
behave. `demo_gate.py` shows the same scoring and refusal deterministically, with no model,
including an untagged scan.

## Findings from testing

Defects and behaviors found while building and testing the tool. The runs behind findings 3
and 5, and the discarded first evaluation attempt behind finding 1, are in
`evidence_development/`.

**1. A scan that times out must not look like a clean scan.** When a scan hits its limit, the
tool returns `status: "timeout", partial: true` and the note "absence of a finding is NOT
evidence of absence", and the agent is told to retry narrower or report the area as untested.
Testing showed that Nuclei's file export (`-jle`) is only written when a scan exits cleanly,
so a killed scan returned zero findings even when it had found something (the first
evaluation attempt's three baselines all ended with 0 findings). The tool now reads findings
from Nuclei's output stream as they arrive. In the evaluation, every timed-out scan kept its
partial findings (2, 1 and 10 in the three runs; 12 in the live gate run). An agent is only as
trustworthy as its tools.

**2. The exclusion list has to hold even when an action is approved.** An early version passed
`approved=True` for every low-risk action, and the tool dropped the whole `-etags` exclusion
list whenever `approved` was true. Allowlisted tags still limited what ran, but a template
tagged both `exposure` and `intrusive` would not have been excluded. Now `-etags` always
applies, and an approval lifts only the approved tag. The live gate run shows it: only
`default-login` was lifted.

**3. An untagged scan is the widest scan, so it must score highest.** A review of the gate
found that a `run_nuclei` call with no tags (only a severity filter) would have scored low and
run most of the template library. Now `tags` is required, an empty list scores high and the
tool refuses it even if approved, and the scored tag list and the exclusion list come from one
source (`policy.toml`), so they cannot disagree. The policy is validated at start-up with a
floor (`high` can only be `ask_human` or `deny`), and its hash is in every audit log. Every
scan in the evaluation carried tags.

**4. The agent's narrative is not evidence; the audit log is.** In a development run, the
report said it had not attempted SQL injection or default credentials. The audit log shows it
ran `sqli` and `default-login` scans. That is why every finding must cite a `call N`. In the
3 evaluation reports and the live gate report, every finding cites a call, and every cited
scan's logged template IDs include the finding.

**5. Prior-knowledge contamination.** In a development run, the agent rated
`POST /rest/user/login` High because it knows Juice Shop is vulnerable, not because of anything
it observed (one HTTP 500). The evidence rule (cite the call, or file it under "Hypotheses for
a human") is the control, and in the evaluation no finding lacked a citation. Smaller traces
remain inside cited findings: every report lists which security headers are "likely" or
"typically" missing from memory, while the scan only reported a count. Juice Shop is a weak
benchmark for the same reason: the model has memorized it. A custom or modified app is the
better test.

**6. The automated consistency check does not work yet.** It compares the report's "did not
test" claims against the tags that ran, by matching tag names near phrases like "no" or "did
not". It flagged all 3 evaluation runs, and every flag was a false positive: for example "the
headers/cors/ssl scan returned no CORS-specific findings" is true, but it gets flagged. It also
misses claims written in prose. The precise version is to have the model emit its "did not
test" list as structured data and compare that set with the log. Until then it is a
heuristic, and its output is not evidence.

## What the agent did and did not decide

- **Plans.** Runs 1 and 3 chose the same four scans; run 2 replaced `tech, backup` with a
  narrower `misconfig, panel` retry after its first scan timed out. All three fetched
  `/metrics` and a Swagger path to confirm.
- **Leads.** All three runs read `cleanupFtpFolder` in the `/metrics` body and none checked
  `/ftp`, a known exposure on this target. Each run did surface the LLM token counters in
  `/metrics` as an undocumented AI integration for a human to investigate. With 13 passive
  tags and GETs, this evaluation cannot separate agent planning from a script that runs the same tags in
  small batches;
  following leads needs a larger action space.

## Known limitations

- Three agent runs on one well-known target. A behavior check, not a reliability result.
- Nuclei detects known exposures and CVEs, not business-logic or auth flaws, which is most of
  what Juice Shop contains. The agent reports those areas as untested.
- **Citations are checkable at template level, not URL level.** The audit log stores a
  summary of each scan (status, count, template IDs), while the model sees each finding's
  matched URL. In the live gate report the agent says two Swagger paths returned HTTP 200;
  only `/api-docs/swagger.json` was fetched, and the log cannot show which path the scan
  matched. Next step: log the matched URLs too.
- The risk scorer is rule-based: tags, plus sensitive-path hints for GETs. A production
  version would be a policy engine (for example OPA) with asset criticality from the asset
  inventory.
- The hash chain catches casual edits, but anyone with write access can rewrite and re-hash
  the whole file, and dropping the last records is undetectable. Production anchors the head
  hash outside the system (KMS-signed, or S3 Object Lock).
- `fetch_url` puts fetched page content into the model's context, so a hostile target could
  try prompt injection through it. Fetched content should be wrapped as untrusted data.
- The approver identity is self-declared (`APPROVER`, or the OS user). Production binds it to
  SSO identity and a change ticket.
- `bedrock.py` retries `ResourceNotFoundException` with backoff. That error normally means a
  wrong model ID, but the Bedrock inference profile returned it intermittently for a valid ID
  during development. Retries are not logged today, and they should be: a silent retry can
  hide a misconfiguration.
- `evidence_clean/_meta.txt` shows `TEMPLATES: v` because of a parsing bug in
  `run_clean.sh`; the template version (v10.5.2) is recorded correctly in every audit log's
  `run_start.meta`.
